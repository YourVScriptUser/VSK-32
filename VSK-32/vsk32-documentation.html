VSK-32 Technical Reference

A software CPU, BIOS and disk stack: a 32-bit fetch-decode-execute core written in Python, a ROM BIOS written in its own assembly dialect, and a flat-file disk format called SSFS underneath it. This document walks through all of it, end to end, from the reset vector to the sector reader.

01 / SYSTEM

§Overview

VSK-32 is a self-contained virtual machine: a Python program emulates a 32-bit processor, memory, a handful of I/O ports and two peripherals (keyboard, disk), and boots a BIOS image the same way real firmware would boot on real hardware. The BIOS reads a boot sector off a virtual disk, hands off to whatever it finds there, and the emulator's job from that point on is simply to keep fetching, decoding and executing instructions.

Three pieces make up the whole stack:

  • The emulator — a Python process that owns memory, registers, ports and timing (Emulator.py, System.py, SuperIO.py).
  • The BIOS — firmware written in VSK-32's own assembly language, assembled into a ROM image the emulator loads at address zero (bios.x32).
  • SSFS — a minimal sector-based file format used on the virtual disk image, plus a host-side tool for reading it (ssfs.py).
SCOPE OF THIS DOCUMENT Everything below is drawn directly from the provided source files. Where a detail (such as an unused assembly mnemonic) isn't demonstrated anywhere in the source, that's called out explicitly rather than guessed at.
02 / SYSTEM

§Runtime architecture

Starting Emulator.py runs through a fixed bring-up sequence before any user code executes:

  1. Imports System and SuperIO; System.py immediately checks it's running on Windows (os.name == "nt") and hides the console cursor.
  2. Allocates a 256 MB memory object, a registers object, and a 256-slot port-I/O buffer.
  3. Starts the interrupt-polling thread (keyboard) and constructs the non-interrupt device handler (disk).
  4. Starts a background thread that redraws the terminal from video memory roughly 30 times a second.
  5. LoadVMBios() loads VM_BIOS/bios.rom into memory at 0x00000000, then EmuRun() verifies VM_DISK/vmdisk.img exists and is exactly 512 MB.
  6. The main loop begins: batches of 500 cpu32.step() + cpu32.interrupt_tick() calls, paced to a 200 kHz theoretical ceiling.
  7. On Ctrl+C or an unhandled host-level exception, Shutdown() runs: final register/flag state is printed, a memory dump is optionally written, and every background thread is joined before exit.
TIMING MODEL The clock isn't a real hardware timer — EmuRun() runs instructions in batches of 500, measures how long the batch took, and sleeps off the difference against a 200 kHz target (TARGET_BATCH_TIME = 500 / 200_000). Actual throughput depends on host CPU speed and Python overhead once instructions get expensive (disk I/O, GUI lock contention).

§CPU & registers

The processor is modeled by the cpu32 class in Emulator.py: a static fetch → decode → execute loop with no pipelining, caching or speculative execution — one instruction fully completes before the next is fetched.

Stack

The stack always moves in 4-byte (dword) units, growing downward:

OpEffect
push valsp -= 4, then writes a dword to [sp].
popReads a dword from [sp], then sp += 4.

Nothing enforces stack bounds or alignment — a runaway stack simply corrupts whatever memory it walks into. The BIOS documents (but the CPU does not enforce) two conventional stack regions: a small BIOS-only stack and a larger kernel stack set up just before jumping to the boot sector — see §12.

04 / SYSTEM

§Memory & address map

Memory is one flat bytearray, 256 MB (256 * 1024 * 1024) in size, addressed 0x00000000–0x0FFFFFFF. Byte, word (16-bit) and dword (32-bit) reads/writes are all little-endian and unaligned-safe (they just index consecutive bytes). Any address past MAX_ADDR raises InvalidMemoryWrite — on both reads and writes, despite the exception's name.

NO MEMORY PROTECTION A source comment notes protection was removed on purpose: "Memory protection has been removed as it bought performance down to the Hz." Any instruction can read or write any address in range, including the IVT, the BIOS's own code, or another process's conceptual "kernel" region. This is a deliberate performance trade-off in the emulator, not an oversight to work around.

Fixed memory regions

0000 0000
– 0000 00FF
Interrupt Vector Table (IVT). 64 dword-sized slots (256B ÷ 4). Slot n lives at address n×4 and holds the 32-bit address of a handler routine.
0B80 0000
– 0B80 0FFF
Video memory. 4096-byte text buffer read by the console refresh thread. See §10.

Everything else in the address space is unreserved as far as the CPU is concerned — regions like the BIOS's own code, the keyboard buffer, or a boot sector are conventions the BIOS defines and respects, not hardware-enforced zones. See §12 for the BIOS's own layout of the low addresses it controls.

05 / SYSTEM

§Instruction encoding

Every instruction is a fixed 8 bytes, decoded field-by-field in cpu32.decode_current_ip() — there is no variable-length encoding:

Byte offsetFieldSizeTypical use
0opcode1 BSelects the operation. Anything not in the 1–33 range faults as UnknownOpcode.
1a1 BFirst operand — almost always a register index.
2b1 BSecond operand — a register index, when the addressing mode needs one.
3–4imm162 B16-bit immediate, used directly by port and 16-bit ops.
5–6extra2 BCombined with imm16 to form a 32-bit immediate.
7flags1 BSelects the addressing-mode variant for opcodes that support more than one.

The 32-bit immediate used by most opcodes is built as imm32 = (extra << 16) | imm16 — the code comments call this "little endian" combination of the two halves. imm16 is also read on its own for the port number in out/in when their flag selects immediate-port mode.

ASSEMBLER NOT INCLUDED The provided sources are the CPU's Python implementation and the BIOS's .x32 assembly source — not the assembler that turns mnemonics like wb [r10], r3 into these eight raw bytes. Everything about opcode numbers and their runtime behavior below comes straight from Emulator.py; the exact bit-packing an assembler would choose for each operand isn't something these files define.

mov addressing modes

OPCODE_INDIR_COPY_DATA is the one instruction with four distinct flag variants, all 32-bit:

flagsDirectionDetail
0register → memoryWrites register a to the fixed address imm32.
1memory → registerReads the dword at fixed address imm32 into register a.
2[register] → registerReads the dword at the address held in register a into register b.
3register → [register]Writes register a to the address held in register b.

Example: BIOS code using several of these together

bios.x32 — keyboard.read_cursor
keyboard.read_cursor:
  ldi r9, KEYBOARD_BUFFER_CURSOR_ADDRESS
  rb r10, [r9]

  ldi r9, KEYBOARD_BUFFER_BASE
  add r10, r9

  ret

This loads the address of the one-byte cursor, reads it, then adds the keyboard buffer's base address to turn the relative cursor into an absolute address — returned in r10.

07 / SYSTEM

§Exceptions & faults

CPU-level faults are handled entirely inside cpu32.step(): a Python exception raised anywhere during decode or execute is caught, mapped to a numeric ISR id, and turned into what is effectively a synthetic interrupt — the same save-and-jump mechanism used for hardware and software interrupts (see §08). Firmware can install a handler for any of these the same way it installs a keyboard handler.

Exception → IVT vector mapping (Emulator.py::cpu32.EXCEPTION_DISPATCH_TABLE)

InvalidMemoryWrite600x000000F0Any memory access (read or write) past 0x0FFFFFFF.

On a fault, before jumping: the ISR id is written to r0 and the faulting instruction's address is written to r1 — a handler can inspect both to decide what happened and where.

TWO SEPARATE ERROR SYSTEMS Don't confuse the in-VM fault mechanism above with the host-level dialogs in Exceptions.warning_window() and System.error_window(). Those call the Windows MessageBoxW API directly and are only used for conditions the emulator itself can't recover from — a missing BIOS file, a missing or wrongly-sized disk image, or an unhandled Python exception in the emulator's own runtime loop. Either dismisses the dialog and then exits the whole process.
08 / SYSTEM

§Interrupts

All three interrupt sources — hardware, software, and CPU exceptions — funnel through the same setup_interrupt_environment() routine: save all 24 registers to the shadow copy, push the current IP onto the stack, then load IP from the target IVT slot.

Hardware interrupts (keyboard)

SuperIO.InterruptHandler runs a dedicated Python thread that polls the keyboard roughly every millisecond using msvcrt.kbhit()/getch(). On a keypress it writes the key's value to the keyboard port (0x4B) and flags interrupt_ready. The CPU only actually notices on the next call to interrupt_tick() — invoked once per step() in the main loop — and only if IF is set. This makes hardware interrupt latency roughly one CPU cycle plus up to ~1ms of polling jitter, not immediate.

A DOCUMENTED RACE, ALREADY FIXED A comment in interrupts.keyboard describes a real bug that was hit during development: a sti; hlt wait-for-input loop could hang forever if interrupts got disabled inside the handler and never re-enabled before returning. The fix is that the keyboard ISR explicitly re-runs sti right before iret, since it can only ever be entered while interrupts were already on.

Software interrupts

The int opcode always fires immediately, regardless of IF — interrupt masking only affects hardware delivery. int 0x05, for example, computes vector 5 × 4 = 0x14 and jumps to whatever address is stored there.

Returning

iret pops IP from the stack and restores r0–r23 from the pre-interrupt snapshot. It does not restore SP or the flag register — a handler that leaves the stack imbalanced, or that changes EQ/HI/LO and doesn't clear them back, will leak that state into whatever resumes.

09 / I/O

§Ports & devices

256 dword-wide ports (SuperIO.portio) sit behind the in/out opcodes. Writing to any port immediately triggers NonInterruptDevicesHandler.PollAllDevices() — so polled devices (currently just the disk) are checked synchronously on every out, not on a timer.

Defined ports (SuperIO.py::PORTs)
PortNamePurpose
0x00STORAGE_STATUS_NOTIFY_PORTSet to 1 to trigger the disk operation currently configured on the other disk ports; the BIOS resets it to 0 immediately after.
0x4BKB_PORTHolds the most recent key code written by the keyboard hardware handler.
0xEASTORAGE_SECTOR_PORTSector number for the pending disk operation.
0xEBSTORAGE_ADDRESS_PORTMemory address to read into / write from.
0xECSTORAGE_STORAGE_MODE1 = read from disk into memory, 2 = write from memory to disk.

Disk device protocol

NonInterruptThreadDevices.Disk.poll() implements the other end of the four disk ports. Its logic on every poll:

  1. If VM_DISK/vmdisk.img doesn't exist, show a fatal warning dialog and stop (this returns without raising a CPU-visible fault — it's a host-level problem).
  2. If the status port isn't set or the mode isn't 1 or 2, do nothing.
  3. Mode 1 (read): if the requested sector is within DISK_END_SECTOR (524288), seek to sector × 1024, read 1024 bytes, and copy them byte-by-byte into memory starting at the address port's value.
  4. Mode 2 (write): reads 1024 bytes out of memory at the address port's value, seeks to the same sector offset, and overwrites that sector on disk.

This gives a 512 MB disk (524288 sectors × 1024 bytes), matching the exact size the emulator checks for at startup.

SYNCHRONOUS AND BLOCKING Disk I/O happens inline, inside whatever thread called PollAllDevices() — normally the CPU's own execution thread, triggered by an out instruction. A slow or failing disk read stalls CPU execution for the duration of the file operation.
10 / I/O

§Video & console

There's no real display hardware — video memory (0x0B800000–0x0B800FFF, 4096 bytes) is just a byte buffer that a background thread translates directly into terminal output, roughly 30 times a second (time.sleep(0.03333) between frames, and only when the frame content actually changed).

Video byte encoding (Emulator.py::spawn_refresh_thread)
Byte valueMeaning
0End of frame — the refresh thread stops scanning here.
10, 32–126Printed as the literal ASCII character (10 is line feed).
130Switches to RED for subsequent characters.
131Switches to GREEN.
132Switches to BLUE.
133Switches to BRIGHT_BLACK (dim gray).
134Switches to CYAN.
135Switches to a red background.
136Resets to the terminal's default color.

Color codes are in-band — they consume a byte position in the buffer just like a printed character, they simply don't produce visible output themselves. Every BIOS string in the string pool opens with one of these codes (usually 133 for status text or 132 for the banner).

The BIOS's own teletype interrupt (ISR 14) writes one character at a time to a single self-tracked cursor byte (print.teletype_cursor), relative to the video base — it never reads back what's already on screen, so it's purely additive until something clears the region (see clear_video in §13).

§Live debugger GUI

A Tkinter window (System.py::GUI) runs on its own thread, started right before the main run loop, and gives a live view into CPU state without pausing execution.

Registers panel

All 24 general registers in hex, each flashing white for one refresh tick (66ms) when its value changes since the last redraw.

IP / SP

Current instruction pointer and stack pointer, always visible.

Flags

EQ / HI / LO / IF shown as filled or hollow dots.

Stack peek

8 dwords above and below SP, auto-redrawn whenever SP moves, with the row containing SP highlighted.

Memory / hex view

A scrollable hex+ASCII dump of a user-chosen address range (capped at 16KB), with quick-jump buttons for the IVT, video memory, current IP, current SP, and page-forward navigation.

Clock & cycles

Sampled every 250ms from cpu32.current_cycle and formatted as Hz / kHz / MHz, alongside a raw running cycle count.

"Follow IP" auto-recenters the hex view as execution moves; toggling it off (or manually editing the address range) freezes the view where you left it. "Pause View" only stops the GUI's own redraw timers — it has no effect on the CPU thread, which keeps running at full speed underneath.

§BIOS memory layout

The BIOS ROM is loaded flat at address zero and is 21 KiB on disk. Everything below is a convention the BIOS source documents in its own header comments — the CPU doesn't know or enforce any of it.

0000 0000
– 0000 1009
Reset vector region. Address zero holds a single jmp 0x0000100A; real BIOS code starts just after.
0000 100A
– 0000 5400
BIOS code, including all interrupt service routines.
0000 5400
– 0000 5BAA
BIOS stack — temporary, used only during early boot before the kernel stack exists. Not enforced by hardware.
0000 5C00
– 0000 6000
Boot sector — sector 0 of the disk is read here by do_boot.
0000 0F00
– 0000 0FFF
Keyboard buffer — 256 bytes, one byte per pending key.
0000 0EFF
Keyboard buffer cursor — a single byte, kept relative to the buffer's base address specifically so the offset always fits in one byte (the buffer is exactly 256 bytes long).
0F00 0000
Kernel-space stack — where the BIOS moves SP to just before jumping into the boot sector.

Boot Sector Header (BSH)

The boot sector loaded to 0x5C00 is expected to follow a fixed layout:

Address rangeField
5C00 – 5C01Boot signature — must be exactly 0x55 0xAA.
5C02 – 5C35Null-terminated OS name string (52 bytes), printed by the BIOS on a successful boot.
5C40 – 6000Boot code — must start and end within this window; this is the exact address the BIOS jumps to.

§Boot sequence

Tracing execution from power-on:

bios.x32 — reset vector
region 0x00000000
jmp 0x0000100A

region 0x0000100A
cli                    ; Interrupts wont work this early
clf                    ; Clear flags
ssp BIOS_STACK_BASE    ; Setup early BIOS stack
jmp bios_entp
  1. Reset vector. Address zero jumps straight past itself to 0x0000100A, disables interrupts (nothing is installed in the IVT yet), clears flags, and sets up a temporary stack.
  2. bios_entp. Initializes the teletype cursor, prints the BIOS banner, then calls setup_devices and setup_interrupts.
  3. setup_devices currently only initializes the keyboard: zeroes the cursor byte and wipes the 256-byte buffer.
  4. setup_interrupts installs five handler addresses into the IVT — see the table in §14.
  5. A long pause (a manual busy-wait loop, twice), purely so boot messages are readable.
  6. do_boot issues a disk-read software interrupt for sector 0 into 0x5C00, then checks the two boot-signature bytes.
bios.x32 — do_boot (signature check)
ldi r0, BOOT_SECTOR_LOAD_ADDRESS
rb  r1, [r0]
cmp r1, 0x55
jne do_boot.bad_sig

add r0, 1
rb  r1, [r0]
cmp r1, 0xAA
jne do_boot.bad_sig

On a bad signature: prints "Boot Failed: Not a bootable disk." and returns to bios_entp, which falls through to an infinite halt loop (die: cli; hlt; jmp die) — the machine sits parked, waiting for nothing, since interrupts were just disabled.

On a good signature: prints the OS name string found at 0x5C02, pauses again, clears the video buffer, zeroes all 24 general registers, moves the stack pointer to the kernel-space stack at 0x0F000000, and jumps to 0x00005C40 — the boot sector's own entry point. From here the BIOS has fully handed off control; only its installed interrupt handlers remain reachable.

§BIOS interrupt ABI

IVT ids 5–20 are reserved by convention for BIOS-provided services; id 1 is the hardware keyboard vector. Four software services and one hardware handler are actually implemented:

Installed by bios.x32::setup_interrupts
ISR idVectorServiceRegisters inTrigger
10x04Keyboard—Hardware, fired by the emulator when a key is pressed and IF is set. Not meant to be invoked with int.
50x14Disk readr0 = sector, r1 = destination addressint 0x05
60x18Disk writer0 = sector, r1 = source addressint 0x06

140x38Teletype (print one character)r0 = ASCII codeint 0x0E
bios.x32 — interrupts.disk_read
interrupts.disk_read:
  ldi r2, 0
  out r2, 0x00      ; clear the status port first

  ldi r2, 1
  out r2, 0xEC      ; mode = read

  out r0, 0xEA      ; sector
  out r1, 0xEB      ; destination address

  ldi r2, 1
  out r2, 0x00      ; notify — this out triggers the actual disk poll

  ldi r2, 0
  out r2, 0x00      ; clear the status port again

  iret

Every disk service follows the same four-port handshake: clear status, set mode, set sector and address, then pulse the status port to 1 — since any out instruction triggers a device poll, this last write is what actually causes NonInterruptThreadDevices.Disk.poll() to perform the transfer synchronously before iret runs.

15 / STORAGE

§SSFS — the disk filesystem

SSFS is a deliberately minimal, flat file format for the virtual disk. There's no free-space map, no subdirectories, no timestamps and no permissions — just a name, a starting sector, and a length.

Layout

  • Sector size: 1024 bytes, matching Vars.DISK_SECTOR_SIZE.
  • The entire directory lives in a single fixed sector: sector 4 (byte offset 4096–5119 of the image).
  • The directory holds up to 34 file entries, each exactly 30 bytes.
  • Sector 0 is reserved separately, outside SSFS's own bookkeeping, as the BIOS boot sector (see §12) — SSFS's reader makes no special case for it, so a filesystem entry could theoretically claim it too if something wrote one there.

Directory entry format (30 bytes)

OffsetSizeField
01 B0xFE — file-entry magic byte. The reader scans byte-by-byte for this to find the next entry.
14 BStart sector (little-endian dword).
54 BLength, in sectors (little-endian dword).
91 B0xFD — filename-descriptor magic. If this byte isn't 0xFD right after the length field, the reader treats the directory as corrupt and aborts.
1020 BASCII filename, NUL-padded to 20 bytes.

The reader (read_by_sector in ssfs.py) walks the 1024-byte metadata sector looking for 0xFE bytes; any byte that isn't a file-entry magic is skipped one at a time. It stops at the end of the sector, and reports a corrupt read if a length field isn't immediately followed by the name magic.

FILE SIZE VS. SECTOR LENGTH The reported _size for a file is always sectors × 1024 — a whole number of sectors. SSFS has no concept of a file's exact byte length within its final sector; anything reading a file has to know (or not care) where the real content ends inside that last 1024-byte block.
16 / STORAGE

§ssfs.py — command-line reader

ssfs.py is a standalone, host-side tool — it reads a .img file directly with plain Python file I/O and has no dependency on the emulator process. It's how you inspect a disk image from outside the VM, independent of the BIOS's own disk-read interrupt.

usage
python ssfs.py ls   <imagepath>
python ssfs.py read <imagepath> <filename> <ascii|hex>
CommandBehavior
ls <imagepath>Reads the directory sector and prints every file's name, size in bytes, and its sector range (start–end).
read <imagepath> <name> asciiPrints the file's raw bytes as characters via chr() — best for text files; non-printable bytes will still print whatever chr() produces.
read <imagepath> <name> hexPrints the file's raw bytes as two-digit hex pairs, wrapped every 30 bytes per line.

An unrecognized read type silently falls back to ascii. Looking up a filename that isn't in the directory, or an image path that doesn't exist, prints an error and exits with status 1 or 2 respectively.

§Shutdown & memory dumps

Shutdown can be triggered three ways: Ctrl+C during the run loop, an unhandled Python exception during the run loop (shown in a "Guru Meditation"-style error dialog with the exception type, a stack trace, and the current IP/flags), or a fatal startup check failing (missing BIOS, missing disk, wrong disk size).

Emulator.Shutdown() then, in order:

  1. Prints final register values, IP, SP, flags, and total cycle count to the console.
  2. If M_DUMP/dump.bin already exists, overwrites it with the entire 256 MB memory image — this is a manual, opt-in dump: the file has to already be present, it's never created automatically.
  3. Stops the GUI thread, signals the keyboard interrupt thread to exit and joins it, then does the same for the screen-refresh thread.
  4. Redirects stdout/stderr to the null device and installs a no-op sys.unraisablehook, specifically to suppress a lingering Tkinter error on shutdown (documented in-line as a workaround, not a design goal).
  5. Frees the in-memory RAM array and exits the process.

§Utility layer (Teknikality.py)

Imported by System.py as Emu.System.Dependencies.Teknikality, this is a general-purpose helper module shared across the project rather than something specific to the CPU or BIOS. The pieces the emulator actually relies on:

  • ANSI color constants (colors class) — used for every console log line the emulator prints.
  • Cursor helpers — hide_cursor() hides the blinking terminal caret via kernel32 so it doesn't visually clash with the video refresh loop.
  • clearscreen() — a thin cross-platform wrapper (cls / clear) used between frames and loading-bar redraws.

The module also contains a much larger set of general-purpose pieces not exercised by the emulator's own boot/run path: a small numeric/string helper library (numbertools, stringtools), a console progress bar (Dynamic_Loading_Bar), a toy cooperative task runner (EasyThreadMultitasking), a custom pseudo-random generator seeded from a continuously-reseeding background thread (_Ran), and a handful of standalone novelty functions (randomized fake system-error message generators, and two intentionally destructive "prank" routines that tear down the Python runtime's builtins) that are dead code as far as this emulator is concerned — nothing in Emulator.py or System.py calls them.

DO NOT CALL THESE give__arrythmia() and sabotage_() deliberately corrupt or delete Python's own builtins and module state for comedic effect. They are unrelated to the emulator's operation and unsafe to invoke in any process you care about.

§File map

Emulator.py

Entry point. Allocates memory/registers/ports, loads the BIOS, runs the timed fetch-decode-execute loop, and owns the cpu32 class with every opcode's behavior.

System.py

Low-level primitives: DwordArray, registers, memory, hex formatting helpers, the Windows platform check, and the Tkinter live debugger GUI.

SuperIO.py

256-port I/O bus, the threaded keyboard interrupt source, and the polled (non-interrupt) disk device.

Exceptions.py

CPU/emulator exception classes, plus a blocking Windows warning-dialog helper.

Vars.py

File paths and disk/sector size constants shared across modules.

ssfs.py

Host-side reader/CLI for the SSFS disk format — independent of the running emulator.

bios.x32

BIOS source in VSK-32 assembly: boot, interrupt handlers, teletype, disk, keyboard. Assembled separately into bios.rom.

Teknikality.py

Shared utility toolkit (colors, small helpers, a loading bar, a task runner) plus unrelated novelty code not used by the emulator.

Compiled from a direct read-through of the provided source: Emulator.py, System.py, SuperIO.py, Exceptions.py, Vars.py, ssfs.py, bios.x32, and Teknikality.py. Points marked "inferred" or "unconfirmed" reflect details the Python source defines behaviorally but that the BIOS assembly never exercises with a visible mnemonic.
